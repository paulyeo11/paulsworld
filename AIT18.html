AIT18: How My Website Actually Deploys —
Claude Code, GitHub, and Vercel AIT18：我的网站到底是怎么部署的——
Claude Code、GitHub 和 Vercel

Every time I ask Claude Code to add a photo or fix a page, something happens between "done" and the change actually showing up on my phone. I asked for a picture of it — here's the actual pipeline, drawn out, with the two gotchas that have bitten me before. 每次我让Claude Code帮我加一张照片或修改一个页面，在它说"完成了"和这个改动真正出现在我手机上之间，其实发生了好几件事。我让它画了一张图出来——这就是真实的流程，还标出了以前坑过我的两个关键点。

The Pipeline, in Order 流程，按顺序来

I ask Claude Code for a change from my phone or my notebook. It edits the file, commits it, and pushes to GitHub — but GitHub only tells the live site to rebuild when the change lands on one specific branch, called main. From there, it fans out to the two hosting services that watch my GitHub repo, and only after Claude checks the real link does it tell me I'm done. 我从手机或笔记本电脑上让Claude Code改点东西。它修改文件、提交（commit），然后推送（push）到GitHub——但GitHub只有在改动落到一个特定的分支上（叫main）时，才会通知网站重新构建。从那里，它会同时发送给两个监听我GitHub仓库的托管服务，而且只有在Claude真正检查过那个链接之后，它才会告诉我"弄好了"。

Why the Branch Has to Land on Main 为什么改动必须落到main分支上

Vercel only rebuilds the site when main changes. On some Claude Code sessions — especially the web/cloud version — the tool is handed a separate working branch instead of writing straight to main. If that branch never gets merged, the commit is real and saved on GitHub, but the live site never hears about it. That's what used to cause the "I asked for a photo and it never appeared" problem. Vercel只有在main分支发生变化时才会重新构建网站。在有些Claude Code会话中——尤其是网页版/云端版——工具被分配到的是一个独立的工作分支，而不是直接写入main。如果那个分支从来没有被合并进去，这次提交虽然是真实的、也保存在了GitHub上，但网站却根本不知道它的存在。这就是以前"我让它加照片，结果照片一直没出现"这类问题的真正原因。

🌿 The Fix🌿 解决方法
  • Every session branch gets merged into main in the same turn — not saved up for later.每一个工作分支都会在同一轮里立刻合并进main——不会留到以后再处理。
  • Direct pushes to main always fetch and rebase first, so a push never gets rejected by someone else's newer commit.直接推送到main之前，一定会先fetch再rebase，这样就不会因为别人有更新的提交而被拒绝。

Two Hosts Watch the Same Push 两个托管平台同时监听同一次推送

Both paulsworld.vercel.app and paulsworld.netlify.app are connected to the same GitHub repository, so in theory one push updates both. In practice, Netlify's free plan ran out of its monthly "operational credits," which pauses new deploys until the plan resets. 无论是paulsworld.vercel.app还是paulsworld.netlify.app，都连接着同一个GitHub仓库，理论上一次推送应该能同时更新两个网站。但实际上，Netlify的免费套餐用完了每月的"运营额度（operational credits）"，导致新的部署被暂停，要等额度重置才能恢复。

⏸️

Netlify is stuck on an old build until 16 August 2026. It isn't broken — the account is just out of free deploy credits for this cycle. Vercel isn't affected and stays the reliable link in the meantime. Netlify会一直卡在旧版本上，直到2026年8月16日。它并没有坏掉——只是这个账号本月的免费部署额度用完了。Vercel不受影响，在此期间它才是可靠的链接。

The Last Step Nobody Sees: Verify Before Reporting 最后一步，谁也看不见：报告之前先验证

A push "succeeding" and a page actually being live are two different things. Before Claude tells me anything is ready, it fetches the real URL itself and checks the change is there — not "check back in a few minutes," an actual look.推送"成功"和页面真正上线，是两码事。Claude在告诉我"弄好了"之前，会自己去抓取那个真实网址，检查改动是不是真的已经出现了——不是"过几分钟再看看"，而是真的去看一眼。

💡

The lesson: a deploy pipeline has more steps than "save the file." The branch has to reach main, the right host has to actually build it, and someone has to look at the result before calling it done. Drawing it out is what made the branch-merge gotcha and the Netlify pause obvious instead of mysterious. 经验教训：一个部署流程远不止"保存文件"这么简单。分支必须真正到达main，正确的托管平台要真的完成构建，还得有人在宣布完成之前去看一眼结果。把它画出来，才让"分支要合并"这个坑和"Netlify暂停"这件事变得一目了然，而不是一头雾水。
